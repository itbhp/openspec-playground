# Workshop Recap — Spec-Driven Development vs Vibe Coding

---

## What We Built

A half-day workshop (expanded to full day) teaching spec-driven development via OpenSpec to a backend-heavy audience, green on OpenSpec but comfortable with agentic AI tooling.

**Stack:** Java 21 · Spring Boot 3.4.5 · Gradle 9.3 · Testcontainers · OpenSpec  
**Domain:** Employee CRUD REST API — persistence changes, domain stays the same.

---

## Key Design Decisions

### The Skeleton
- All five CRUD operations stubbed and working in-memory from the start
- `EmployeeRepository` is a custom interface, not Spring Data — intentional, enables clean persistence swaps without touching controller or service
- No tests exist at the start — that's Act 1's job
- JPA and DynamoDB dependencies commented out in `build.gradle`, ready to uncomment per act
- `openspec/config.yaml` pre-configured — attendees don't run `/opsx-init` and don't waste time on project initialization

### The Three Acts
- **Act 1** — vibe coding: write tests with no spec, no constraints. Produces inconsistency. That's the point.
- **Act 2** — spec-driven: MySQL migration via OpenSpec. Half-baked prompt, not copy-paste.
- **Act 3** — spec as memory: DynamoDB migration building on the archived MySQL change.

### The Prompts
Deliberately half-baked. Give direction, not prescription:
- Act 2: mention MySQL, JPA, Testcontainers, contract must be maintained. Nothing else.
- Act 3: mention DynamoDB, AWS SDK v2, LocalStack, keep controller and service unchanged. Nothing else.

The gap between the prompt and the proposal is where the learning happens.

### Git Flow
Each attendee creates one personal branch from main at the start of Act 2 and stays there all day. No merges, no PRs, no shared branches. The branch is a personal sandbox.

### openapi-generator
Removed entirely. Dead weight. Focus is exclusively on OpenSpec.

## Intentional Traps

### The `@Repository` Bean Ambiguity (Act 2)
When the JPA adapter is added, Spring finds two beans implementing `EmployeeRepository` and fails with `NoUniqueBeanDefinitionException`. Not flagged to attendees. Tests Spring knowledge. Fix is a one-liner (`@Primary` on the new adapter, or remove `@Repository` from `InMemoryEmployeeRepository`). A good proposal review catches it before apply.

### The `config.yaml` Staleness (Act 2 → Act 3)
After archiving the MySQL migration, `config.yaml` may or may not update `Active persistence` automatically — depends on the model, not guaranteed. Some attendees will get it updated, some won't. This is intentional chaos. It surfaces live, visibly, and makes the review argument concrete. Not a tool failure — a discipline question.

### The Hot Partition / UUID Break (Act 3)
The Act 3 prompt says "keep controller and service unchanged." Sequential `Long` IDs are poor DynamoDB partition keys — hot partition risk at scale. UUID fixes it but breaks the API contract (`@PathVariable Long id` in the controller). The trap: the constraint in the prompt smuggles in the ID type assumption without stating it. A mid-level dev misses it. An experienced AWS engineer catches it. The debate that follows is the best moment in the workshop.

## Insights from the Dry Run

### Mid-level dev perspective
- Goes HTTP boundary, `@SpringBootTest`, `TestRestTemplate` — correct instinct
- Catches the `@Repository` ambiguity by reading the proposal before applying
- Reads the DynamoDB proposal, feels uncertain about `Long` IDs, asks the room
- The uncertainty is the right response — and it only happens because there's a proposal to read

### Staff engineer perspective
- Walks in skeptical — "I'd catch this in code review anyway"
- The hot partition moment changes the read: without the proposal there's no pause, without the pause there's no question, without the question it ships
- The spec didn't catch it. The review culture the spec enforces caught it. That's the distinction.
- Remaining concern: `config.yaml` drift at scale needs tooling, not discipline

### The Open Floor Retry
After Act 3, attendees redo the MySQL migration with vibe coding only — no OpenSpec. After everything they've experienced, the absence of the spec feels like losing a safety net. This is the hammer. Don't skip it.

## The Honest Conclusion

Three failure modes, none of them zero:

| Approach | Failure mode |
|----------|-------------|
| Vibe coding | Fails silently and unpredictably. No record of what was decided or why. |
| Spec-driven | Fails loudly and traceably. Paper trail exists. Post-mortem has a starting point. |
| Confluence + manual code | Fails slowly and expensively. You're reading documentation for a system that no longer exists. |

**The real value of SDD is not at post-mortem time. It's at 3am on a Monday with an incident open and a manager pinging on Slack.** You know what changed, when, and why it was approved. You get to the problem faster.

SDD is not the cure. The failure modes are different. The recovery cost is lower.

---

## The Production Gap

The workshop proves the value of the discipline. It doesn't prove the discipline is sustainable at scale.

What's missing:
- A linter that validates `config.yaml` consistency against the codebase
- A PR check that flags when code changed but no OpenSpec file changed
- A staleness indicator on archived changes when referenced files have been modified

Without tooling, the workflow runs on team discipline and presenter energy. That works for a workshop. It degrades under scale, turnover, and deadline pressure — exactly when you need it most.

**That's the gap between a good workshop and a production-ready workflow.** Worth stating honestly in the final discussion.

---

## One Line Per Key Lesson

- The AI is fast. The AI is capable. The AI has no memory and no contract. That's the problem.
- The spec doesn't catch everything. The human review of the spec does.
- A PR that changes code but not the spec is incomplete.
- The proposal is editable. Edit it before applying. It's cheaper than debugging after.
- The archive is not documentation. It's context for the next change and for the 3am incident.
- Predictable is not the same as correct. Review is what makes it correct.
